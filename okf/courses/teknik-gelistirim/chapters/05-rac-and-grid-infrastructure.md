# Özet

In this chapter, the student learns how active-active Oracle Real Application Clusters (RAC) clustering and Oracle Grid Infrastructure provide high availability, operational redundancy, and horizontal scalability for enterprise database workloads. The curriculum covers private Interconnect networking, High Availability IP (HAIP), Cache Fusion block transfers, and Global Resource Directory (GRD) synchronization over shared Automatic Storage Management (ASM) disk groups. Additionally, students examine Oracle Maximum Availability Architecture (MAA) Silver, Gold, and Platinum tiers for Oracle Database 18c and 19c alongside dynamic workload management using SCAN listeners, Dynamic Database Services, and Fast Application Notification (FAN).

### Objective 1: Configuring Grid Infrastructure, Private Interconnect Networks, HAIP, Cache Fusion, and GRD Lock Coordination

* **Grid Infrastructure and Clusterware Architecture:** The student learns that Oracle Grid Infrastructure combines Oracle Clusterware and Automatic Storage Management (Oracle ASM) into a single software stack that sits between the operating system and database instances [1, 2]. Oracle Clusterware provides the required infrastructure to run Oracle RAC [2, 3] and manages high-availability resources such as Virtual Internet Protocol (VIP) addresses, databases, listeners, and services [2, 4].
  * **Cluster Synchronization Services (CSS):** CSS tracks node membership across the cluster, monitors node responsiveness, and executes node eviction if a node fails or loses communication to prevent split-brain scenarios [1, 5].
  * **Cluster Ready Services (CRS) / Cluster Ready Services Daemon (CRSD):** CRSD manages high-availability resources including VIPs, Single Client Access Name (SCAN) listeners, database instances, and services, automatically restarting or relocating failed resources [1, 6].
  * **Event Manager (EVM) / Event Manager Daemon (EVMD):** EVM publishes cluster events and alerts generated by Clusterware components to initiate rapid failover routines [1, 7, 8].
* **Private Interconnect Network and HAIP Configuration:** The student learns that Oracle RAC requires dedicated private network connectivity, known as the interconnect, used exclusively for inter-node and inter-instance communication [1, 9].
  * **Interconnect Functionality:** The private interconnect network handles internal cluster communication, heartbeat signals, and Cache Fusion data block transfers directly between instance System Global Areas (SGAs) without writing data to disk [1, 10, 11].
  * **High Availability IP (HAIP):** High Availability IP (HAIP) or operating system level network interface card (NIC) bonding uses multiple physical NICs through Redundant Interconnect Usage to guarantee high throughput and zero downtime if an interconnect NIC fails [1, 12].
  * **Verification:** Database administrators verify private interconnect configuration and active interfaces by querying the dynamic performance views V\\(CLUSTER_INTERCONNECTS and V\\)CONFIGURED_INTERCONNECTS [13, 14].
* **Cache Fusion and Global Resource Directory (GRD) Coordination:** The student learns that Cache Fusion is a diskless cache coherency mechanism in Oracle RAC that transfers copies of data blocks directly from the memory cache of a holding instance to a requesting instance over the high-speed private interconnect [1, 10, 15-17].
  * **Resource Coordination:** Global Cache Service (GCS) and Global Enqueue Service (GES) coordinate buffer cache blocks and enqueues in the Global Resource Directory (GRD) [15, 18].
  * **GRD Functionality:** The GRD is distributed across all active instances [1, 10, 15] and tracks the state, location, and lock status of every cached data block across all nodes to maintain transactional consistency [1, 10, 15].
  * **Background Processes:** Global Cache Service Processes (LMS / LMSn) record data file statuses and cached block information in the GRD, control message flow, and transmit block images between instance buffer caches [18-21]. Global Enqueue Service Monitor (LMON) monitors global enqueues and resources across the cluster and performs global enqueue recovery [18, 22, 23]. Global Enqueue Service Daemon (LMD) manages incoming remote resource requests within each instance [18, 22, 24].
* **Version Application:** Redundant Interconnect Usage / HAIP is available in Oracle Grid Infrastructure 11g Release 2 (11.2) and later [12]. Official manuals document these concepts for Oracle Database 19c [13, 15, 25, 26]. The training architecture notes apply Grid Infrastructure, private Interconnect, and Cache Fusion to IFS Applications (IFS Cloud, IFS Applications 10/9) [1].

### Objective 2: Evaluating Oracle MAA Reference Tiers, Active-Active Clustering, and Disaster Recovery

* **Oracle High Availability Framework and MAA:** The student learns that Oracle Maximum Availability Architecture (MAA) provides an Oracle best practices blueprint based on proven Oracle high availability technologies and recommendations to remove complexity in designing an optimal high availability architecture [27].
  * **High Availability Blueprint Scope:** The official manual High Availability Best Practices and Overview for Release 19 structures high availability best practices across Oracle RAC and Clusterware best practices, Oracle Data Guard best practices, and MAA Platinum with Oracle GoldenGate best practices [28].
  * **Disaster Recovery Strategy:** For comprehensive protection against disasters, including data corruptions and regional disasters, Oracle recommends combining Oracle Data Guard with Oracle RAC [29].
* **Active-Active Node Clustering Mechanics:** Active-Active Node Clustering using Oracle Real Application Clusters (RAC) enables multiple database instances running on separate physical servers to concurrently access a single shared database [3, 10, 30, 31] hosted on shared Automatic Storage Management (ASM) disk groups [10, 32-34].
  * **Multi-Node Resource Execution:** In an active-active cluster, every node runs its own set of memory structures (SGA) and background processes [10]. All active nodes actively accept connections and process concurrent transactions from application server pools [10].
  * **Application Redundancy:** Active-active clustering ensures continuous availability, operational redundancy, and seamless horizontal scalability for IFS mid-tier application server pools in IFS Applications (IFS Cloud, IFS Applications 10/9) [10].
  * **Service-Level Prioritization:** On the service level, DBAs can define Gold, Silver, and Bronze services mapped to Resource Manager consumer groups to prioritize application workloads [35].
* **Version Application:** High Availability Best Practices and Overview is documented for Release 19 [28, 36]. Real Application Clusters Administration and Deployment Guide is documented for 19c [25, 26, 37]. Active-active node clustering is applied to IFS Applications (IFS Cloud, IFS Applications 10/9) in the training architecture notes [10].

### Objective 3: Administering Dynamic Database Services, SCAN Listeners, and FAN in Oracle Database 18c and 19c

* **Dynamic Database Services Administration:** Dynamic Database Services enable DBAs to group database workloads, route work to optimal instances, and achieve high availability [38, 39].
  * **User-Defined Service Requirement:** Oracle Database automatically creates a default database service (identified by DB_NAME, DB_UNIQUE_NAME, or PDB_NAME), but Oracle strongly recommends that clients do not use default database services for application connections; DBAs should create user-defined dynamic database services using SRVCTL or Oracle Enterprise Manager [40-43].
  * **Resource Manager and Deployment Placement:** Services integrate with Oracle Database Resource Manager to map services to consumer groups and priorities [35, 44]. Services can be configured as singleton (running on one server instance at a time) or uniform (running across all active servers in a server pool) [45-47].
* **Single Client Access Name (SCAN) and Listener Routing:** Single Client Access Name (SCAN) is a single network name defined in DNS or Grid Naming Service (GNS) that round-robins to three IP addresses [48], allowing clients to connect without changing client connection strings when nodes are added to or removed from the cluster [48, 49].
  * **Connection Routing Workflow:**
    1. The client connects to SCAN (which includes a SCAN VIP on a public network) and provides a valid service name [50].
    2. The SCAN listener determines which database instance hosts the service and routes the client to the local node listener on that node [50, 51].
    3. The local node listener (listening on a node VIP and port) connects the client to the instance on the local node [50].
  * **HTTP Protocol Awareness:** Starting in Oracle Database 12c Release 2 (12.2), SCAN listeners support HTTP protocol awareness to redirect HTTP clients across cluster nodes [51, 52].
  * **Valid Node Checking:** Valid Node Checking for Registration (VNCR) restricts dynamic service registration with SCAN listeners to valid nodes and subnets [53-56].
* **Fast Application Notification (FAN) and Connection Load Balancing:** Fast Application Notification (FAN) is part of the Oracle RAC high availability framework that publishes real-time cluster state notifications (UP and DOWN events for instances, services, nodes, networks, and load balancing metrics) [39, 57, 58].
  * **ONS Transport:** All clients beginning with Oracle Database 12c Release 2 (12.2) use Oracle Notification Service (ONS) to receive FAN events [49].
  * **Failure Interruption:** FAN notifies integrated Oracle clients (JDBC Thin, OCI, ODP.NET, Universal Connection Pool, WebLogic Server Active GridLink) immediately when failures occur, breaking clients out of TCP/IP timeouts and preventing application hangs [39, 57, 59, 60]. Integrated clients use FAN DOWN events to clean up terminated connections immediately, and FAN UP events to route new connections to newly available instances [57, 58, 61, 62].
  * **Connection Load Balancing:** Client-side load balancing (configured via LOAD_BALANCE=ON in client connection definitions) balances initial requests across SCAN listeners [51, 63]. Server-side load balancing uses SCAN listeners to direct connection requests based on the service connection load balancing goal (-clbgoal LONG or SHORT) [46, 51, 64], with Oracle recommending -clbgoal LONG for server-side load balancing [46, 64].
  * **Runtime Load Balancing:** Runtime connection load balancing uses Load Balancing Advisory events published via ONS (SERVICEMETRICS) with -rlbgoal SERVICE_TIME or THROUGHPUT to allocate connections in connection pools based on current service quality [49, 65-68].
* **Session Draining and Continuous Availability:** FAN planned DOWN events trigger session draining at request boundaries, enabling active work to complete without exposing errors to end users before taking an instance offline [69-73].
  * **Version Application:** Server-side session draining during planned maintenance was introduced in Oracle Database 18c [69-71, 73]. Transparent Application Continuity (TAC) was introduced in Oracle Database 18c as a functional mode of Application Continuity enabled by setting FAILOVER_TYPE=AUTO on database services [74-76]. In Oracle Database 19c, TAC automatically tracks session and transactional state to enable transparent failover and safe replay boundaries [75-77].
