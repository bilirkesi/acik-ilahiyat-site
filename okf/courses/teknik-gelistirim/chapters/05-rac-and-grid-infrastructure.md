# Özet

In this chapter, the student learns how active-active Oracle Real Application Clusters (RAC) clustering and Oracle Grid Infrastructure provide high availability, operational redundancy, and horizontal scalability for enterprise database workloads. The curriculum covers private Interconnect networking, High Availability IP (HAIP), Cache Fusion block transfers, and Global Resource Directory (GRD) synchronization over shared Automatic Storage Management (ASM) disk groups. Additionally, students examine Oracle Maximum Availability Architecture (MAA) Silver, Gold, and Platinum tiers for Oracle Database 18c and 19c alongside dynamic workload management using SCAN listeners, Dynamic Database Services, and Fast Application Notification (FAN).

# Öğrenme Hedefleri

1. The student can configure Oracle Grid Infrastructure and private Interconnect networks using High Availability IP (HAIP) to enable Cache Fusion data block transfers and Global Resource Directory (GRD) lock coordination in Oracle RAC environments.
2. The student can evaluate Oracle Maximum Availability Architecture (MAA) Silver, Gold, and Platinum reference tiers for Oracle Database 19c to implement active-active clustering and disaster recovery solutions.
3. The student can administer Dynamic Database Services, Single Client Access Name (SCAN) listeners, and Fast Application Notification (FAN) in Oracle Database 18c and 19c to enable automated connection load balancing and high availability failover.

### Objective 1: Configuring Grid Infrastructure, Private Interconnect Networks, HAIP, Cache Fusion, and GRD Lock Coordination

* **Grid Infrastructure and Clusterware Stack Architecture:** The student learns that Oracle Grid Infrastructure combines Oracle Clusterware and Automatic Storage Management (ASM) into a single software stack that runs between the operating system and database instances [1]. Oracle Clusterware manages cluster membership, monitors node and process health, and coordinates high-availability resources including Virtual Internet Protocol (VIP) addresses, Single Client Access Name (SCAN) listeners, database instances, and database services [1-5]. Cluster Synchronization Services (CSS) tracks node membership across the cluster and handles node eviction during failures or loss of communication to prevent split-brain scenarios [1, 5]. Event Manager (EVM) publishes cluster events and alerts generated by Clusterware components to initiate rapid failover routines [1, 6].
* **Private Interconnect Network and HAIP Configuration:** The student learns that Oracle RAC requires dedicated private network connectivity, referred to as the interconnect, used exclusively for inter-instance communication between servers in the cluster [7]. The private Interconnect handles internal cluster communication, heartbeat signals, and Cache Fusion data block transfers directly between instance System Global Areas (SGAs) without writing data to disk [1, 2, 8, 9]. High Availability IP (HAIP) or operating system level network interface card (NIC) bonding uses multiple physical network cards to guarantee high throughput and zero downtime if an Interconnect NIC fails [1]. Redundant Interconnect Usage is available in Oracle Grid Infrastructure 11g release 2 (11.2) and later for Oracle RAC databases [10]. DBAs verify private interconnect configuration and settings by querying the dynamic performance views V\\(CLUSTER_INTERCONNECTS and V\\)CONFIGURED_INTERCONNECTS [11, 12].
* **Cache Fusion and Global Resource Directory (GRD) Coordination:** The student learns that Cache Fusion is a diskless cache coherency mechanism in Oracle RAC that transfers copies of data blocks directly from the memory cache of a holding instance to a requesting instance via the private Interconnect [1, 2, 9, 13-15]. Global Cache Service (GCS) and Global Enqueue Service (GES) coordinate buffer cache blocks and enqueues within the Global Resource Directory (GRD) [15-18]. The GRD is distributed across all active instances and tracks the state, location, and lock status of every cached data block across all nodes to maintain transactional consistency [2, 16, 17]. Global Cache Service Processes (LMS) record data file statuses and cached block information in the GRD, control message flow, and transmit block images between instance buffer caches [19-21]. Global Enqueue Service Monitor (LMON) monitors global enqueues and manages enqueue recovery [19, 22], while Global Enqueue Service Daemon (LMD) handles incoming remote resource requests and deadlock detection [18, 19].
* **IFS Applications Context:** In an IFS Applications environment (specifically IFS Cloud, IFS Applications 10, and IFS Applications 9), active-active Oracle RAC clustering ensures that high-volume mid-tier application server connection pools remain performant and highly available [1, 2]. The training program notes state that a slow or misconfigured Interconnect introduces latency into GRD locks and Cache Fusion block exchanges, directly impacting IFS OLTP transaction processing times [1].

### Objective 2: Evaluating Oracle MAA Silver, Gold, and Platinum Reference Tiers for Oracle Database 19c

* **Maximum Availability Architecture (MAA) Framework:** The student learns that Oracle Maximum Availability Architecture (MAA) provides best practice guidelines for designing, implementing, and operating database high availability across four reference architecture tiers: Bronze, Silver, Gold, and Platinum [23, 24].
* **Silver Reference Tier:** The Silver Tier builds upon Bronze by incorporating clustering technology (Oracle RAC or Oracle RAC One Node) for high availability and automatic failover within a data center [25, 26]. Oracle RAC uses an active-active architecture that enables multiple database instances running on separate servers to simultaneously read and write to the same shared database [27, 28]. In Silver tier Oracle RAC deployments, server failover is instantaneous with a brief brownout before service resumes, achieving a recovery time objective (RTO) of seconds for database instance or server failures with zero data loss (RPO = zero) [26, 29]. Oracle RAC One Node provides an active-passive failover option where only one database instance is open during normal operation, delivering server failover in minutes at reduced cost [29-31]. Silver tier clustering eliminates downtime for planned hardware, operating system, or database patch maintenance by executing rolling updates across cluster nodes [25, 26, 29, 32].
* **Gold Reference Tier:** The Gold Tier builds upon Silver by adding database replication technology (such as Oracle Active Data Guard) to eliminate single points of failure and protect against data corruptions, database failures, and site outages [33-35]. Gold uses Oracle RAC as the standard for server high availability [34]. Oracle Active Data Guard maintains synchronized physical standby databases at a remote location using real-time log replication [35, 36]. In the Gold tier, RTO is reduced to seconds or minutes and RPO is zero when using Data Guard synchronous transport (Maximum Availability mode) or near-zero when using asynchronous transport (Maximum Performance mode) [33, 36, 37]. Gold incorporates Data Guard Fast-Start Failover to automate database failover in less than 60 seconds without manual intervention [36, 38]. Active Data Guard standby databases can be opened in read-only mode to offload ad-hoc queries and reporting workloads from the primary database [39].
* **Platinum Reference Tier:** The Platinum Tier builds upon Gold to provide zero outage operations for Platinum-ready applications, protecting in-flight transactions and enabling zero downtime maintenance, upgrades, and platform migrations [40, 41]. Platinum introduces Application Continuity to replay in-flight requests following recoverable session failures, masking outages to end users [42, 43]. Platinum incorporates Oracle Active Data Guard Far Sync to achieve zero data loss failover (RPO = zero) over long distances without performance overhead on the primary database [44, 45]. Platinum utilizes Oracle GoldenGate bi-directional replication combined with Active Data Guard for zero downtime maintenance and cross-platform migrations [46, 47]. Platinum uses Global Data Services (GDS) for automated workload routing, load balancing, and inter-database service failover across replicated database instances [48, 49].
* **Version Application:** The official MAA white papers and reference guides describe the Silver, Gold, and Platinum reference tiers for Oracle Database, with specific MAA best practices detailed for Oracle Database 18c and 19c [23, 24, 50, 51]. Where general MAA tier definitions do not restrict a capability to a single version, the sources present them as core MAA architecture standards.

### Objective 3: Administering Dynamic Database Services, SCAN Listeners, and FAN in Oracle Database 18c and 19c

* **Dynamic Database Services Administration:** The student learns that Dynamic Database Services allow database administrators to group database workloads, route work to optimal instances, and enforce resource management rules using Oracle Database Resource Manager [52-54]. Oracle strongly recommends creating user-defined dynamic database services using SRVCTL or Oracle Enterprise Manager for application connectivity, rather than using default database services (such as DB_NAME, DB_UNIQUE_NAME, PDB_NAME, SYS\\(BACKGROUND, or SYS\\)USERS) [55-58].
* **Single Client Access Name (SCAN) and Listener Routing:** Single Client Access Name (SCAN) is a single network name defined in DNS or Grid Naming Service (GNS) that round-robins to three IP addresses on the public network, enabling clients to connect to the cluster without changing connection strings when nodes are added or removed [59, 60]. Incoming client connection requests contact a SCAN listener, which load balances requests across active instances providing the requested service and routes the client to a local node listener on a node VIP [59, 61-63]. Starting in Oracle Database 12c Release 2 (12.2), SCAN listeners support HTTP protocol awareness to redirect HTTP clients across cluster nodes [62, 64].
* **Connection Load Balancing and Advisory Metrics:** Oracle Net Services supports client-side load balancing (configured via `LOAD_BALANCE=ON` in client connection definitions) and server-side load balancing via SCAN listeners [62, 63, 65]. The Load Balancing Advisory monitors service performance metrics and generates FAN events (`SERVICEMETRICS`) to advise connection pools on directing incoming work [60, 66-70]. DBAs configure connection load balancing goal (`-clbgoal`) to `LONG` (recommended for server-side and client-side load balancing) or `SHORT` (for run-time load balancing) via SRVCTL [71-76]. DBAs configure run-time connection load balancing goal (`-rlbgoal`) to `SERVICE_TIME` or `THROUGHPUT` via SRVCTL to direct work based on current service quality [68, 74, 76, 77].
* **Fast Application Notification (FAN) and Client Integration:** Fast Application Notification (FAN) is part of the Oracle RAC high availability framework that publishes real-time cluster state notifications (UP and DOWN events for instances, services, nodes, networks, and load balancing metrics) via Oracle Notification Service (ONS) [54, 60, 78-81]. Starting with Oracle Database 12c Release 2 (12.2), all clients (including JDBC Thin, OCI, and ODP.NET) use Oracle Notification Service (ONS) for FAN events [60, 82]. Integrated Oracle clients and connection pools (such as JDBC Universal Connection Pool, WebLogic Server Active GridLink, OCI session pools, and ODP.NET connection pools) subscribe to FAN events to execute Fast Connection Failover (FCF), immediately breaking TCP/IP timeout hangs, cleaning dead connections on DOWN events, and routing connections to newly available instances on UP events [60, 69, 79, 80, 83-89].
* **Session Draining and Version Context:** For planned maintenance, FAN planned DOWN events trigger session draining at request boundaries, enabling active work to finish without exposing errors to end users before taking an instance offline [79, 90-92]. Server-side session draining during planned maintenance was introduced in Oracle Database 18c [92-95]. Transparent Application Continuity (TAC) was introduced in Oracle Database 18c as a functional mode of Application Continuity enabled by setting `FAILOVER_TYPE=AUTO` on database services [92, 96, 97]. In Oracle Database 19c, TAC automatically tracks session and transactional state to enable transparent failover and safe replay boundaries for OCI, ODP.NET, and Java applications [98-100].
